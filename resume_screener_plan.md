# План итогового проекта НИС — Resume Screener Bot

**Telegram-сервис скрининга резюме на базе LLM**
_Документ-план для перехода к реализации_

---

## 0. Краткое резюме проекта

Resume Screener Bot — это Telegram-бот, который принимает резюме кандидата и текст вакансии, а на выходе выдаёт структурированный разбор резюме и оценку соответствия вакансии с объяснением. Вся ML-логика построена на вызовах LLM по API с управлением через системные промпты.

**Ключевая инженерная идея:** сервис даёт измеримый структурированный результат (категория резюме, извлечённые поля, скор соответствия), а значит позволяет честно посчитать метрики качества на размеченной тестовой выборке. Это закрывает самый сложный для LLM-проектов блок оценивания.

| Параметр | Значение |
|---|---|
| Формат | Telegram-бот (aiogram) |
| Предметная область | HR / скрининг резюме |
| ML-компонент | LLM по API (Anthropic Console, ключ `sk-ant-api03-…`) |
| Основная ML-задача для метрик | Классификация резюме по категории профессии |
| Baseline без ML | TF-IDF + логистическая регрессия |
| Главные метрики | Accuracy, macro-F1, confusion matrix |
| Цель | Максимальный балл по всем 4 блокам (100/100) |

## 1. Идея и обоснование

### 1.1 Проблема

HR-специалисты тратят значительное время на первичный отбор резюме: нужно прочитать каждое, понять профиль кандидата, сопоставить его с требованиями вакансии и принять решение «смотреть дальше или нет». При большом потоке откликов это рутинная и утомительная работа, в которой легко пропустить подходящего кандидата или потратить время на нерелевантного.

### 1.2 Решение

Бот автоматизирует первичный скрининг: HR (или кандидат для самопроверки) отправляет резюме и вакансию, получает структурированный разбор и обоснованную оценку соответствия. Решение принимает человек — бот ускоряет и структурирует первичный этап, а не заменяет финальное решение.

### 1.3 Почему именно ML / LLM

- Резюме пишутся в свободной форме: разные структуры, формулировки, синонимы навыков, опечатки. Жёсткие правила и регулярные выражения плохо справляются с этой вариативностью.
- Оценка соответствия требует «понимания смысла» (например, «работал с контейнеризацией» ≈ требование «Docker»), что хорошо ложится на языковую модель.
- LLM через системные промпты позволяет быстро менять логику (новые поля, новые критерии) без переобучения.

**Честный ответ на вопрос «можно ли без ML»:** частично да — простой baseline (TF-IDF + логрег) решает задачу классификации категории. Именно поэтому в проекте baseline реализуется и сравнивается с LLM — это и есть обоснование выбора подхода через метрики, а не «по умолчанию взяли нейросеть».

## 2. Архитектура

### 2.1 Слои

Проект разделён на слои с чёткой ответственностью, чтобы избежать «монолитного скрипта» и обеспечить заменяемость модели.

| Слой | Ответственность | Технологии |
|---|---|---|
| Bot (интерфейс) | Приём сообщений Telegram, валидация ввода, форматирование ответа | aiogram |
| Service (бизнес-логика) | Оркестрация: парсинг → скоринг, обработка ошибок, сборка ответа | Python |
| LLM (адаптер модели) | Абстракция над провайдером, отправка промптов, парсинг JSON-ответа | anthropic SDK / интерфейс |
| Prompts (конфиг) | Системные промпты как версионируемые файлы | YAML / txt |
| Eval (качество) | Метрики, baseline, замеры latency и стоимости | scikit-learn, pytest |

### 2.2 Заменяемость модели

Слой LLM скрыт за абстрактным интерфейсом. Это даёт баллы за «возможность заменить модель» и страхует на случай исчерпания кредитов Console — можно переключиться на локальную модель через Ollama для тестов.

```python
class LLMClient(ABC):
    @abstractmethod
    def complete(self, system_prompt: str, user_msg: str) -> str: ...

# anthropic_client.py -> Console API key (sk-ant-api03-...)
# local_client.py      -> Ollama, бесплатно, для отладки и сравнения
```

### 2.3 Поток данных (для диаграммы)

1. Пользователь отправляет резюме + вакансию в Telegram.
2. Bot валидирует ввод (длина, формат, не пустое) и передаёт в Service.
3. Service вызывает LLM-адаптер с промптом парсинга → получает JSON с полями резюме.
4. Service вызывает LLM-адаптер с промптом скоринга (резюме + вакансия) → получает скор и объяснение.
5. Service собирает ответ, обрабатывает ошибки (невалидный JSON, таймаут API).
6. Bot форматирует и отправляет результат пользователю.

**На защиту:** нарисовать эту схему как блок-схему или C4-Container diagram (можно в draw.io / Excalidraw / Mermaid). Это обязательный элемент Блока 3.

## 4. Требования и MVP

### 4.1 Формализация задачи

**Целевая аудитория:** HR-специалисты и рекрутеры малых/средних компаний; во вторую очередь — кандидаты для самопроверки соответствия вакансии.

**Пользовательские сценарии:**

- Рекрутер отправляет резюме и текст вакансии → получает скор соответствия и краткое объяснение сильных и слабых сторон.
- Рекрутер отправляет только резюме → получает структурированный разбор (навыки, опыт, грейд, образование).

**Ограничения:**

- Текстовый ввод на первом этапе (без парсинга PDF/DOCX в MVP).
- Один язык интерфейса для начала (русский или английский).
- Лимит на длину входа из-за контекстного окна и стоимости токенов.

**Нефункциональные требования:**

- Время ответа на один запрос — ориентир до ~10–15 секунд.
- Обработка ошибок API без падения бота (таймаут, невалидный JSON, превышение лимита).
- Воспроизводимый запуск по инструкции (Docker).

### 4.2 MVP

**Входит в MVP:** приём текста резюме + вакансии в Telegram; структурированный разбор резюме; скор соответствия с объяснением; обработка ошибок; метрики на тестовой выборке.

**НЕ входит в MVP (и почему):** парсинг PDF/DOCX (усложняет, не влияет на демонстрацию ML-логики); база данных и история (не нужна для основного сценария); мультиязычность (расширение, а не ядро); интеграция с ATS (отдельный большой блок).

### 4.3 План развития (roadmap)

1. **Загрузка файлов:** парсинг PDF/DOCX резюме, чтобы убрать ручное копирование текста.
2. **Пакетный режим:** загрузка нескольких резюме и ранжирование кандидатов по скору под одну вакансию.
3. **Интеграция с ATS / Google Sheets:** выгрузка результатов скрининга в рабочие инструменты рекрутера.

**Риски проекта:**

- Исчерпание кредитов Console → митигация: локальная модель через Ollama в LLM-слое.
- Галлюцинации LLM (выдуманные навыки) → митигация: строгий промпт «отвечай только на основе текста», постобработка и валидация JSON.
- Предвзятость модели при оценке кандидатов → отметить как этическое ограничение: бот помогает, но финальное решение за человеком.

## 5. Метрики, тестирование и производительность

### 5.1 Датасет

- Источник: открытый «Resume Dataset» (Kaggle) с резюме, размеченными по категориям профессий, либо собственная небольшая размеченная выборка.
- Разбить на train (для baseline) и test (для замеров); зафиксировать размер выборки в отчёте.

### 5.2 Метрики качества

| Метрика | Зачем | Как интерпретировать |
|---|---|---|
| Accuracy | Общая доля верных категорий | Базовый ориентир, но чувствителен к дисбалансу классов |
| Macro-F1 | Баланс precision/recall по классам | Главная метрика при неравных классах |
| Confusion matrix | Где модель путается | Показать наглядно, какие категории смешиваются |

**Сравнение с baseline:** посчитать те же метрики для TF-IDF + логрег и для LLM. Вывод про trade-off (точность vs стоимость vs скорость) — это прямой ответ на критерий «обоснованный выбор модели» и «понимание trade-off’ов».

### 5.3 Производительность

- Замер latency: среднее и p95 время ответа на запрос.
- Оценка стоимости: цена одного запроса в токенах и в долларах (доступна, так как используется Console API с пер-токенным биллингом).
- Поведение на длинных входах: проверить очень длинные резюме (близко к лимиту контекста).
- Базовый нагрузочный тест: несколько параллельных запросов, фиксация деградации.

### 5.4 Тестирование

- [ ] Unit-тесты схем (pydantic): корректный и некорректный JSON от модели.
- [ ] Тест оркестрации screener (с замоканным LLM-клиентом).
- [ ] Тест обработки невалидных данных (пустой ввод, слишком длинный ввод).
- [ ] Тест форматирования ответа бота.

_Минимум 3–5 unit-тестов — обязательное требование Блока 2._

## 6. Доступ к модели и биллинг

**Важно:** подписка Claude (Pro/Max) и доступ к API — это разные продукты с раздельной оплатой. Логин от подписки не даёт ключ для программного доступа из своего кода. OAuth-токен подписки предназначен для Claude Code как инструмента, а не для произвольного бэкенд-сервиса, и его использование для своего приложения нестабильно и нарушает условия использования.

Для бота нужен обычный API-ключ (`sk-ant-api03-…`) из Anthropic Console с пер-токенной оплатой. Новым пользователям API дают небольшой стартовый кредит — для прогона тестовой выборки и демо учебного проекта этого, как правило, достаточно.

**Бонус для оценки:** пер-токенный биллинг Console позволяет честно посчитать стоимость запроса — это закрывает пункт «оценка стоимости (если API)» в Блоке 2, который иначе пришлось бы выдумывать.

### 6.1 Переменные окружения (.env.example)

```
TELEGRAM_BOT_TOKEN=your_telegram_token
ANTHROPIC_API_KEY=sk-ant-api03-...
LLM_PROVIDER=anthropic        # anthropic | local
LLM_MODEL=claude-...
REQUEST_TIMEOUT=30
```

## 7. Этапы реализации (порядок работы)

Рекомендуемый порядок — от ядра к обвязке, чтобы как можно раньше иметь рабочий сценарий.

| Этап | Что сделать | Результат |
|---|---|---|
| 1. Каркас | Структура папок, .env, requirements, абстрактный LLMClient | Проект собирается, ключ читается |
| 2. LLM-слой | anthropic_client + промпты parse/score, парсинг JSON | Из скрипта получаем разбор резюме |
| 3. Логика | screener.py: parse → score, pydantic-схемы, обработка ошибок | Полный флоу работает в коде |
| 4. Бот | aiogram-обработчики, валидация, форматирование ответа | Рабочий Telegram-бот |
| 5. Метрики | Датасет, baseline, run_metrics, confusion matrix | Таблица метрик + сравнение с baseline |
| 6. Производительность | Замер latency, стоимости, нагрузочный тест | Цифры для отчёта |
| 7. Тесты | 3–5 unit-тестов критических функций | pytest зелёный |
| 8. Упаковка | Dockerfile, docker-compose, README, диаграмма | Воспроизводимый запуск по инструкции |
| 9. Демо и защита | Видео/live-демо, презентация на 5 минут | Готовность к сдаче |
